# 自动同步 · 方案分析

> 状态：分析稿，未改代码。目标是把 WebDAV 同步从「手动点一下」升级为「自动、可靠、可配置」。
> 结论：**不要直接在现有快照模型上加速度触发**，先把同步正确性和远端存储模型补齐，否则自动同步只会更快地放大流量、覆盖和照片丢失问题。

## 1. 现状（代码事实）

| 环节 | 现状 |
|---|---|
| 触发 | 仅「WebDAV 同步」页的「立即同步」，没有后台任务 |
| 远端布局 | `IntimateTracker/backup-yyyyMMdd-HHmmss.zip`，每次一份，保留 14 份 |
| 包内容 | `manifest.json` + `tracker.db` + `photos/`（整个 `filesDir/images`）+ `avatars/` |
| 合并 | 下载最新 zip → 逐行 LWW 合并 partner / 4 类字典 / record（含 5 张关联表）→ 上传新 zip → 删旧份 |
| 变更判断 | `record.dataVersion()`（record/partner/字典的 `MAX(updated_at)`）对比 `sync.local_version` + 最新文件 ETag/文件名 |
| 并发 | 无互斥；仅设置页的 `busy` 防连点 |
| 网络 | OkHttp connect 15s / read 60s / write 60s；HTTP 明文被允许 |

## 2. 自动同步前必须解决的 5 个问题

### 2.1 照片根本没有参与合并（正确性）

`mergeFromArchive()` 只合并 partner、字典和 record，**没有合并 `photo` 表**。远端 zip 里的照片文件会被解压到本地 `images/`，但对应的 `photo` 行不会写入，所以：

- 另一台设备新增的照片，本机永远看不到；
- 照片删除也只删本机行/文件，另一端不会同步删除。

`dataVersion` 也不含 `photo` 表，且 `photo` 没有 `updated_at`，所以只加/删照片时会被判定「本地没变化」，直接 `NoChange` 返回，连上传都不会发生。

**要做**：给 `photo` 加 `updated_at`（Room v1→v2 迁移），合并 photo 行与墓碑，合并时复制对应文件，`dataVersion` 纳入照片。

### 2.2 每次同步都上传整包照片，且保留 14 份

一次同步会把整个照片库重新打包上传；14 份快照意味着照片被存 14 遍。举例：照片 150MB 时云占用约 2.1GB，每小时自动同步一天要上传 3.6GB。

**要做**：把远端拆成「当前快照 + 历史」：

```
IntimateTracker/
  current.zip                  # 唯一最新状态，覆盖写（先 .tmp 再 MOVE）
  history/backup-20261023.zip  # 每天首次成功同步留一份，保留 14 天
```

日常同步只覆盖 `current.zip`；历史按天保留，云占用从「14 × 全量」降到「1 + 14 天日备」。

### 2.3 上传不是原子的

`WebDavClient.put()` 直接 PUT 到最终文件名；上传中断会在远端留下半截 zip。`latestRemote()` 又按文件名取最新，下一台设备可能下载到坏包。

**要做**：PUT `current.zip.tmp` → 成功后 `MOVE` 覆盖 `current.zip`；`latestRemote` 只认 `current.zip`；校验失败回退到最近一份日备。

### 2.4 没有单飞与失败退避

自动同步会同时存在周期任务、回前台触发、手动点击三种入口。当前 `SyncManager.sync()` 没有互斥，两个协程可能同时下载/合并/上传，互相覆盖。

**要做**：`SyncManager` 内 `Mutex` 串行化（同一进程内有效）；WorkManager 用唯一任务名 `KEEP`；失败按指数退避重试，认证/配置错误不重试。

### 2.5 冲突粒度是「整条记录」

`mergeRecords()` 按 `record.updated_at` 整条覆盖。自动同步越频繁，两端同时编辑同一条记录、字段互相覆盖的概率越高。

这一步不建议在自动同步里解决；保持 LWW，但在文档/设置里说明「同一记录以最后修改的一端为准」。字段级合并是另一个量级的工程。

## 3. 触发方式对比

| 方案 | 及时性 | 可靠性 | 耗电/流量 | 实现成本 |
|---|---|---|---|---|
| A. 打开/回前台检查 | 中 | 高（用户在用） | 低 | 低 |
| B. 编辑后防抖 2 分钟 | 高 | 中（进程可能被杀） | 中 | 中 |
| C. WorkManager 周期（≥15 分钟） | 低 | 高（系统调度） | 可控 | 中 |
| D. 每次保存立即入队 | 最高 | 中 | 高 | 中 |
| E. 充电/息屏时同步 | 低 | 高 | 最低 | 中 |

**推荐组合：A + B + C**

- 周期任务：默认 1 小时（可选 15 分钟 / 1 小时 / 6 小时 / 每天）；
- 回前台：距上次成功同步超过设定周期才触发一次；
- 编辑后：2 分钟防抖入队，且与上次同步间隔 < 15 分钟时跳过；
- 保留「立即同步」作为兜底。

## 4. 推荐架构

### 4.1 调度层

- 引入 `androidx.work:work-runtime-ktx` + `androidx.hilt:hilt-work`，`SyncWorker` 用 `@HiltWorker`；
- 周期任务唯一名 `sync-periodic`，约束：网络可用；可选「仅 Wi-Fi」「仅充电」；
- 一次性任务 `sync-now`（手动/回前台）与 `sync-debounce`（编辑后），`ExistingWorkPolicy.KEEP`；
- 设置变更时 `cancelUniqueWork` + 重新入队；
- 失败：`Result.retry()` + 指数退避；401/403/404/配置缺失 `Result.failure()`。

### 4.2 大文件与前台服务

全量 zip 在弱网下可能超过 WorkManager 10 分钟限制。建议所有自动同步都用 `setForeground()`（低优先级通知「正在同步」），需要：

- `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` 权限（targetSdk 36）；
- 通知渠道（静默、不显示任何记录内容）；
- 若后续把包体降下来，可改成仅超过阈值才前台。

### 4.3 同步流程（改造后）

1. 取互斥锁，读配置与 `lastSync`；
2. PROPFIND `current.zip`（ETag / size / lastModified）；
3. 本地无改动且远端 ETag 未变 → `NoChange`；
4. 下载 `current.zip` → 合并 record/partner/字典/**photo**；
5. 若合并后仍无变化且远端较新 → 只更新本地版本号，不上传；
6. WAL checkpoint → 打包新 `current.zip`；
7. PUT `.tmp` → MOVE 覆盖 `current.zip`（有 ETag 时带 `If-Match`，412 则重下合并重试一次）；
8. 当天首次成功 → 复制一份 `history/backup-YYYYMMDD.zip`；
9. 更新 ETag / 本地版本 / 上次同步时间；清理超过 14 天的日备。

### 4.4 设置与状态 UI

WebDAV 页新增：

- 自动同步开关（默认关；配置好 URL/账号后可开）；
- 频率：15 分钟 / 1 小时 / 6 小时 / 每天；
- 仅 Wi-Fi（默认开）、仅充电（默认关）；
- 上次同步时间、结果、最近一次错误；
- 「立即同步」保留。

通知只写「亲密记录正在同步 / 同步失败，点按查看」，不出现任何数据内容。

### 4.5 安全

- 自动同步在后台无用户在场，凭据仍从加密存储读取；
- 建议自动同步开启时要求 HTTPS（当前 manifest 允许明文），或至少弹窗警告；
- 日志不打印 URL 中的账号、密码、文件名中的时间以外的信息。

## 5. 分阶段落地

| 阶段 | 内容 | 预估 |
|---|---|---|
| P0 正确性 | photo 表合并 + Room v2 迁移 + dataVersion 纳入照片 + 原子上传 + 互斥 | 1–1.5 天 |
| P1 远端模型 | `current.zip` + 每日历史 + If-Match / 412 重试 | 0.5–1 天 |
| P2 自动调度 | WorkManager + Hilt Worker + 前台通知 + 设置项 + 状态 | 1 天 |
| P3 触发与打磨 | 回前台检查、编辑防抖、失败提示、双端测试 | 0.5–1 天 |

**总计约 3–4.5 天**（不含字段级合并）。

如果只想先上一个「能用」的版本：可以只做 P2 的每日一次自动同步，复用现有快照模型；但照片跨设备不同步、云占用随照片增长这两个问题会保留，不建议长期这样。

## 6. 测试计划

- 双端：A 加记录/照片 → B 同步可见；B 删除 → A 同步后消失；
- 只加照片不改记录：确认能触发上传；
- 断网/飞行模式：任务重试、不产生半截文件；
- 上传中杀进程：远端无坏 `current.zip`，下次能恢复；
- 错误密码 / 404 / 500 / 坚果云这类无 ETag 服务；
- 两端同时改同一条记录：整条 LWW 结果符合预期；
- 大照片库（>100MB）：前台通知、耗时、10 分钟限制；
- Doze / 小米后台限制：周期任务延迟情况，设置页给出说明。

## 7. 需要确认的决策

1. 远端是否接受从「14 份全量快照」改成「current.zip + 14 天日备」？
2. 默认频率与约束：建议 **1 小时 + 仅 Wi-Fi**，充电约束默认关，是否同意？
3. 照片同步修复需要 Room v1→v2 迁移，是否本次一起做？
4. 同一记录多端同时编辑仍是整条 LWW，是否接受？

## 8. 附：只做「每次打开软件触发同步」可行吗？

**结论：可行，而且作为个人双设备的第一步最划算；但「每次打开」必须节流，并且要先修 4 个前置问题，否则会变成「每次打开都传一遍照片」。**

### 8.1 为什么可行

- 打开 App 时用户在场、通常有网，失败也能当场重试；
- 「打开就是最新」符合直觉，不需要解释后台同步；
- 不用引入 WorkManager，不依赖系统调度，省电、实现简单（估计 0.5–1 天）。

### 8.2 但「每次」不能是字面意思

`ON_RESUME` 在切后台、解锁、分屏、配置变化时都会触发，一天可能几十次。建议：

- 只在**冷启动**或**从后台回到前台**时检查；
- 距上次尝试 ≥ 15–30 分钟才真正发起；
- 已经在同步（`Mutex` 未拿到）直接跳过；
- 用户正停留在新增/编辑表单时跳过本次，避免打包与保存竞争；
- 等首帧渲染完、解锁后再开始，不阻塞启动。

保留「手动立即同步」作为兜底；触发逻辑封装成 `SyncScheduler.maybeSyncOnOpen()`，以后加 WorkManager 时不用改调用点。

### 8.3 只做打开触发的 4 个前置条件

1. **原子上传**：`.tmp` + MOVE，否则打开时网络一断就可能留下坏包；
2. **单飞**：打开触发 / 手动 / 以后的周期任务共用一把锁；
3. **无新改动不回传**：现在是「只要不是 NoChange，下载合并后一定再上传一份」。另一台设备同步过之后，本机每次打开都会：下载整包 → 合并 0 条 → 又上传整包，云端很快堆满重复快照。应改成「合并后本地没有新改动就只更新版本号，不上传」；
4. **照片参与合并 + dataVersion 含照片**：否则「打开同步」也同步不到另一台设备的照片，只加照片时还会被判定无变化。

另外，`push()` 是 `WAL checkpoint` 后直接复制 db 文件；如果用户刚打开就开始编辑，复制过程中新写入只在 WAL 里，zip 可能漏掉刚保存的记录（不丢本地数据，但远端快照滞后）。打开触发会提高这个概率，建议改成 `VACUUM INTO` 或短暂只读快照。

### 8.4 流量与云占用（最现实的问题）

假设照片库 150MB：

- 打开时有本地改动 → 上传 150MB；
- 另一台设备有新数据 → 下载 150MB + 当前逻辑再上传 150MB；
- 14 份快照上限下，每次打开产生的快照都会挤掉旧的，云端长期维持 14 × 150MB ≈ 2.1GB。

一天打开 10 次、其中 3 次有变化，就是 ~450MB 上传/下载。个人 Wi-Fi 环境可接受，移动网络不友好，所以「仅 Wi-Fi」开关几乎是必须的。

**如果能同时把远端改成 `current.zip` + 每日历史，打开触发的成本会降到「每次只覆盖一个文件」**，这是最理想的组合。

### 8.5 不做的代价

- App 不打开就不同步：另一台设备的改动要等下次打开才可见（对个人使用通常可接受，因为看数据时一定会打开）；
- 同步中断（进程被杀）只能等下次打开重试；原子上传能保证远端不坏，但不能保证这次传完；
- 没有「后台自动备份」的安心感，适合作为第一阶段，后续再加周期任务。

### 8.6 推荐落地顺序（只做打开触发）

1. 原子上传 + 单飞 + 「无新改动不回传」（P0，约 0.5–1 天）；
2. 照片表合并 + Room v2 + dataVersion（P0，约 1 天）；
3. `SyncScheduler.maybeSyncOnOpen()`：冷启动/回前台 + 15 分钟节流 + 编辑页跳过 + 状态展示（0.5 天）；
4. 设置项：自动同步开关、仅 Wi-Fi、上次同步结果（0.5 天）。

合计约 **2.5–3 天**，比完整方案（3–4.5 天）少的主要是 WorkManager 和周期调度。

如果照片库很小、且只在一台设备上用，甚至可以只做第 1、3 步先跑起来；但跨设备照片不同步的问题仍然存在。
